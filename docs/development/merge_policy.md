# マージポリシー

## 原則

- `main` への直接 push は禁止する。
- `main` への変更は PR を必須とする。
- PR はレビュー完了後にのみマージ可能とする。

## 必須ステータスチェック

`main` へマージする PR には、次のチェック通過を必須とする。

- Workflow: `PR Quality Gate`（`.github/workflows/ci.yml`）
- Job: `lint`
- Job: `typecheck`
- Job: `test`

`main` への `push` では同 workflow 内で `build` を実行し、デプロイ前品質ゲートとして扱う。

### 必須チェックとPRブロック条件の対応

| 種別 | 対象 | ブロック条件 | 対応 |
|------|------|--------------|------|
| PR必須 | `lint` | 失敗/未実行 | `npm run lint` をローカル再実行し、lintエラーを解消 |
| PR必須 | `typecheck` | 失敗/未実行 | `npm run typecheck` をローカル再実行し、型エラーを解消 |
| PR必須 | `test` | 失敗/未実行 | `npm run test` をローカル再実行し、失敗テストを修正 |
| main必須 | `build` | 失敗 | `npm run build` をローカル再現し、`lint/typecheck/test` を順に修正 |

セキュリティ関連修正を含む PR でも同一の必須チェック（`lint/typecheck/test`）を適用する。

## Dependabot脆弱性対応SLA

- 重大（Critical）脆弱性: 検知後、即時に対応PRをレビューし、最短で当日中にマージする。
- High 脆弱性: 検知日から 1週間 以内に対応PRをマージする。
- Medium/Low 脆弱性: 通常の週次Dependabot運用で計画的に解消する。
- 期限内に対応できない場合は、PRコメントで理由・暫定緩和策・対応期限を明記する。

## 環境変数・シークレットのレビュー必須項目

- 環境変数 の追加/変更がある場合、Dev/Stg/Prod の接続先分離が説明されていることを 必須 とする。
- シークレット の追加/変更がある場合、GitHub/Vercel/Supabase の秘密管理に設定する手順が記載されていることを 必須 とする。
- `service_role` の利用範囲がサーバコンテキスト限定であることを明記する。
- Preview から Prod への接続経路を追加する変更は PRブロック 対象とする。

## セキュリティレビュー観点（必須）

- SQLインジェクション対策（パラメータ化クエリ）が維持されていること。
- XSS対策（HTMLエスケープ/サニタイズ）が維持されていること。
- 認証/認可の境界（RLS、特権鍵の利用範囲）が維持されていること。

## PR本文のIDトレース必須項目

すべてのPRで、本文に次の項目を必須入力とする。

- 対象ID（`FNC-xxx` / `SCR-xxx` / `IF-xxx` / `TBL-xxx`）
- 要件ID（`FR-xxx` / `NFR-xxx` / `CON-xxx` / `AC-xxx`）
- テストID（`TC-xxx` / `TS-xxx`）
- テスト証跡リンク（CI実行結果、テストログ、スクリーンショット等）

### 記載ルール

- 空欄は禁止。該当なしの場合は `N/A（理由）` を明記する。
- 複数ある場合は改行またはカンマ区切りで列挙し、識別子は省略しない。
- IDは設計書の定義値と一致させる（例: `FNC-001`, `AC-010`）。
- 証跡リンクは第三者が辿れるURLまたはリポジトリ内パスを記載する。

### セキュリティ記載欄（PR本文必須）

PR本文に次のセキュリティ確認欄を設け、該当有無を記載する。

- 入力検証: 追加/変更した入力項目のバリデーション内容
- 認可: 誰がどの操作を実行できるか、権限境界の変更有無
- シークレット: 新規シークレット追加有無、平文コミットの有無

## PRブロック条件

以下のいずれかに該当する場合は PRブロック とし、修正完了までマージ不可とする。

- 必須 ステータスチェック（`lint/typecheck/test`）が未通過。
- PR本文の必須項目（対象ID/要件ID/テストID/テスト証跡）が未記載。
- 環境変数 の変更理由と適用環境（Dev/Stg/Prod）が不明。
- シークレット を平文でコミットしている、または秘密管理への移管手順がない。
- Preview から Prod へ到達し得る設定変更がある。

## 障害時の一次切り分け手順

1. `lint` 失敗: `npm run lint` を再実行し、静的解析エラーを修正する。
2. `typecheck` 失敗: `npm run typecheck` を再実行し、型定義と実装の不整合を修正する。
3. `test` 失敗: `npm run test` を再実行し、失敗テストと依存設定を修正する。
4. `build` 失敗: `npm run build` で再現し、ログ順に `lint/typecheck/test` を個別に切り分ける。

## 例外運用

緊急対応時も原則PR経由とし、事後に必ずレビュー記録を残す。
