## 1. リリース概要
### 1.1 目的
- 本手順書は、MVP構成（Vercel/Supabase/GitHub Actions）に整合した再現可能なリリース手順を定義する。
- 失敗時の切り戻しを標準手順として組み込み、`NFR-003`（可用性）と`NFR-006`（RPO/RTO）を維持する。

### 1.2 リリース対象
- Webアプリ（Vercel）: 機能変更・不具合修正
- DB（Supabase/Postgres）: マイグレーション
- セキュリティ関連設定: `policy_settings` 等の更新（監査必須）

### 1.3 デプロイ方式
- アプリ: GitHub Actions -> Vercel 本番デプロイ
- DB: GitHub Actions または Supabase CLI によるマイグレーション適用
- リリース戦略: 後方互換を維持した段階的適用（Expand/Contract）
- 停止方針: 原則無停止。例外時の計画停止は15分以内（超過見込み時は実施中止して再計画）。

### 1.4 リリース承認条件（Go/No-Go）
- PR品質ゲート（lint/typecheck/test）通過
- DB変更の適用検証（差分レビュー、ロールバック可否確認）完了
- スモークテスト項目の事前確認完了
- バックアップ正常性確認（直近日次バックアップ）
- 承認者の最終承認（通常/緊急ともにaliyell）
- 単独運用時の補償統制（自己承認時はチェックリスト、実施ログ、24時間以内の事後レビューを必須化）

### 1.5 不足情報への推奨回答（2026-02-11確定）
| 項目 | 推奨回答 |
| -- | -- |
| SLO詳細閾値 | 5xx率: Warning `>=2%/10分` かつ `総リクエスト>=100`、Critical `>=5%/5分` かつ `総リクエスト>=50`。Auth失敗率: Warning `>=15%/15分` かつ `試行>=40`、Critical `>=30%/5分` かつ `試行>=20`。 |
| オンコール体制 | P1は24/7対応（一次応答15分以内）、P2/P3は平日09:00-19:00 JST対応（一次応答60分以内）。 |
| 承認フロー | 通常承認者: aliyell。緊急時最終判断者: Incident Commander（aliyell）。 |
| DBマイグレーション方針 | 破壊的変更は同一リリースで禁止。Expand/Contractの2段階を必須化。 |
| ダウンタイム許容時間 | 計画停止は最大15分。15分超見込みならGo不可。 |
| ユーザー通知チャネル | 公式Webお知らせを一次チャネル、ログイン画面/メンテ画面を二次チャネルとする。 |

## 4. 切り戻し手順 (Rollback)
### 4.1 切り戻し判断基準
以下のいずれかを満たした場合、Release Managerは切り戻しを宣言する。
- スモークテストの必須項目が1件以上不合格
- P1事象（ログイン不能、DB接続不可、重大5xx増加）が15分以上継続
- データ整合性問題が確認され、即時の安全復旧が困難
- APPI観点で利用者影響が拡大するリスクが高い

### 4.2 切り戻し手順
| No | 管理ID | 手順 | 担当 | 完了条件 |
| -- | -- | -- | -- | -- |
| 1 | REL-RB-001 | インシデント宣言、追加変更を停止、連絡網へ通知 | Incident Commander | 宣言/通知完了 |
| 2 | REL-RB-002 | Vercelを直前安定デプロイへ切替（前回デプロイIDを再有効化） | App Owner | 前版稼働 |
| 3 | REL-RB-003 | DBロールバック実施（後方互換ならdown migration、非互換ならバックアップ復元） | DB Owner | DB整合性確認 |
| 4 | REL-RB-004 | 主要機能の再スモークテスト実施 | QA/SRE | 合格 |
| 5 | REL-RB-005 | 切り戻し完了報告、暫定対策、恒久対策チケット起票 | Release Manager | 報告/起票完了 |

### 4.3 DBロールバック方針
- 非破壊変更: down migrationで戻す。
- 破壊的変更: 同一リリースで禁止（Expand/Contractの2段階運用）。やむを得ない場合はリリース自体を延期し、別計画で実施する。
- 復元後は監査ログ整合性、退会削除SLA関連データの整合性を必ず確認する。

### 4.4 切り戻し後確認項目
- ログイン/主要機能/退会導線が前版で正常
- 5xx率/Auth失敗率/P95遅延がベースライン復帰
- 監査ログ出力（`trace_id`含む）が継続
- 利用者影響の告知有無を判断し、必要時は告知実施

## 5. リリース後確認
### 5.1 監視確認（T+24hまで）
- MON-001: 5xx率
- MON-002: Auth失敗率
- MON-003: 主要画面P95（目標3.0秒以下）
- MON-004: 削除ジョブ失敗件数
- MON-005: 通知到達率

### 5.2 問い合わせ対応
- P1問い合わせは即時一次対応（目標15分以内）
- P2問い合わせは営業時間内で優先対応
- 利用者影響が広範な場合は障害告知を実施（一次: 公式Webお知らせ、二次: ログイン画面/メンテ画面）
- APPI該当時は法定フローを優先し、初動60分以内に報告要否判定を行う

### 5.3 リリースレビュー
- 24時間以内に「結果レビュー」を実施し、課題は`Decision Log`に登録
- Error Budget消費が大きい場合は次回リリースを安定化優先へ切替
