## 1. テストの目的と範囲

### 1.1 テスト目的
- FR/NFR/CON に対する受入条件（`AC-001`〜`AC-034`）を満たすことを証跡付きで確認する。
- リスクが高い領域（認可/RLS、退会削除SLA、同意版管理、監査ログ完全性、業務日付境界）を重点的に検証する。
- リリース判定（2026-04-01 予定）に必要な品質根拠を提供する。

### 1.2 In Scope
- 機能: `FNC-001`〜`FNC-013`（認証/同意、習慣管理、チェックイン、履歴、設定、退会、運用通知/監査）。
- 画面: `SCR-001`〜`SCR-008`（`SCR-006` は任意機能としてリスク低で実施）。
- IF/運用: `IF-001`〜`IF-005`、`BAT-003`、`BAT-004`。
- 非機能: 性能（`NFR-001/002`）、セキュリティ（`NFR-004`）、削除SLA（`NFR-005`）、監査/運用（`NFR-007/008/009`）。

### 1.3 Out of Scope
- MVP対象外機能（課金、コミュニティ、ユーザー向け通知多チャネル）。
- 外部サービス内部品質（Google/Supabase内部実装）。
- 本番運用後の長期実績値（`NFR-003`の月間稼働率実績そのもの）。

## 2. テストの段階と定義

### 2.1 テストレベル定義（UT/IT/ST/UAT）

| レベル | 目的 | 主対象 | 主担当 | 入口条件 | 出口条件 |
| -- | -- | -- | -- | -- | -- |
| UT | モジュール単位の正しさを担保 | `M-002/004/005/008/009/014` など | 開発者 | 実装完了、静的解析通過 | 重大バグ0、主要分岐網羅 |
| IT | IF/DB/RLS/監査連携を担保 | `IF-001`〜`IF-005`、`TBL-001`〜`TBL-010` | 開発者+QA | UT完了、結合環境利用可 | `AC-005/010/012/018/020/022/026` 合格 |
| ST | 業務シナリオと非機能を担保 | 主要ユーザーフロー、性能/セキュリティ | QA | IT主要欠陥収束 | Must要件シナリオ合格、P1/P2未解決0 |
| UAT | 受入判定と運用成立性を担保 | `AC-001`〜`AC-034` | プロダクトオーナー（aliyell） | ST完了、受入環境証跡準備 | 受入条件High全件Pass |

### 2.2 テストタイプ定義
- 機能テスト: 正常/準正常/異常/境界/状態遷移/権限。
- 非機能テスト: 性能、セキュリティ、運用/監査、法令運用（APPI）。
- セキュリティテスト実施方式: 手動観点チェックのみ（外部自動スキャンはMVP対象外）。
- 回帰テスト: Must機能の高リスク経路を毎回実行。
- 探索的テスト: UI遷移・エラー体験・アクセシビリティの補完確認。

### 2.3 リスクベース戦略

| リスク区分 | 対象 | 密度方針 | 主な技法 |
| -- | -- | -- | -- |
| High | `FR-023..026`, `FR-002..005`, `FR-010..014`, `NFR-004/005/009` | UT+IT+ST+UATで多層検証 | 境界値、状態遷移、デシジョンテーブル |
| Medium | `FR-006..009`, `FR-017..022`, `NFR-001/002/007/008` | IT+ST中心、UATで代表確認 | 同値分割、境界値、ペアワイズ |
| Low | 任意機能・表示上の軽微項目 | ST探索的中心 | 探索的テスト |

### 2.4 テストID体系
- テスト仕様ID: `TS-[機能IDまたは非機能ID]`（例: `TS-FNC-006`、`TS-NFR-004`）。
- テストケースID: `TC-[レベル]-[主トレースID]-[3桁]`。
- 例: `TC-IT-SCR-002-001`、`TC-UAT-FR-023-002`。

### 4.1 コミュニケーション

- 重大障害: 即時エスカレーション（P1/P2）。

## 5. テスト環境・ツール

### 5.1 環境構成
- Dev: 開発者向け結合検証。
- Stg: UAT/性能/セキュリティ実施用（本番相当設定、単一環境で確定）。
- Prod相当条件: Stgで再現（機密データはダミー）。

### 5.2 ツール
- テスト管理: Markdown（本ディレクトリ）+ 必要時Spreadsheet。
- バグ管理: GitHub Issues。
- API/DB確認: Supabase SQL Editor / CLI。
- E2E自動化候補: Playwright。
- API自動化候補: Postman/Newman もしくはHTTPテストスクリプト。
- 性能試験: `k6`（`NFR-002` の同時10ユーザー検証に採用）。
- セキュリティ試験: 手動チェックリスト実行（認証/認可/RLS/監査証跡観点）。

### 5.3 テストデータ方針
- 完全ダミーデータ生成（確定）。
- 退会/RLS/監査は複数ユーザー（A/B/ROLE-002）を固定シード化。
- APPI対応は模擬インシデントデータで実施（実事故データ不使用）。

## 6. 合格基準・完了条件

### 6.1 品質目標（ゲート判定基準）
- 要件カバレッジ:
  - Must FR + High AC: 100%
  - Should FR/AC: 90%以上
  - Must NFR: 100%
- 欠陥基準:
  - Sev1/P1 = 0件
  - Sev2/P2 = 0件
  - Sev3以下は回避策合意済みであること
- セキュリティ基準:
  - 重大/高脆弱性 = 0件
  - RLS違反 = 0件
- 削除SLA基準:
  - 60秒以内参照不可化、5分以内完全削除（`AC-023`）
- 非機能基準:
  - `AC-027`/`AC-028`/`AC-030`/`AC-034` 合格

### 6.2 完了条件
- 計画対象ケースの実施率100%。
- 受入証跡（画面ログ/DB差分/監査ログ/通知記録/試験レポート）が保管済み。
- 確認ゲート0〜5が承認済み。

## 8. 回帰テスト・自動化計画

### 8.1 自動化対象
- スモーク（PR）:
  - ログイン/同意フロー
  - 習慣作成/更新/アーカイブ/再開
  - チェックイン/冪等/取消
  - RLS拒否/監査必須項目
  - 設定変更/入力バリデーション
- 回帰（main/nightly）:
  - ストリーク/履歴表示
  - 退会SLA（60秒/5分）
  - 閾値通知・通知到達記録
  - 性能計測（k6）

### 8.2 自動化手段
- E2E: Playwright
- API/DB回帰: HTTPテスト + SQL検証
- 性能: k6
- 手動継続: セキュリティ観点診断、APPI訓練証跡確認

### 8.3 CI/CD実行タイミング
- PR: スモーク一式（Failでマージブロック）
- main: スモーク + 機能回帰
- Nightly: 退会SLA、通知運用、性能回帰
- RC: 全自動回帰 + 手動ゲート（セキュリティ/APPI）
