## 1. テスト方針

### 1.1 基本方針
- 要件トレーサビリティを必須化する（各ケースは `FR/AC` と `FNC/SCR/IF` の最低1つに紐付ける）。
- リスクベースで密度を変える（High領域は多層、Low領域は探索的中心）。
- 合否は「実測値/ログ/DB差分」で判定し、曖昧な表現を禁止する。

### 1.2 対象ブラウザ/OS/デバイス
- 優先ブラウザ: Chrome Latest（必須）。
- 準拠確認: Safari Latest（macOS/iOS）、Chrome Android Latest。
- OS: macOS（必須）、iOS/Android（主要シナリオのみ）。

### 1.3 テストデータ準備方針
- 原則: 完全ダミーデータのみ使用（実個人情報不使用）。
- ユーザーセット:
  - `USER-A`（ROLE-001、標準）
  - `USER-B`（ROLE-001、他人データ検証用）
  - `OPS-1`（ROLE-002、運用検証用）
- データ初期化はケース単位で再現可能にする（SQL/fixtureで定義）。

### 1.4 外部連携テスト方針
- `IF-001`（Google認証）: Stgで実接続、Devはモック許容。
- `IF-003`（通知）: 検証用単一通知先で実送信確認。
- `IF-005`（CLI/SQL）: 運用者権限で手動実行し証跡保存。

### 1.5 非機能試験の実施方式
- 性能試験: `k6` を使用し、`NFR-002`（同時10ユーザー）を検証する。
- セキュリティ試験: 手動観点チェックのみ（外部自動スキャンは実施しない）。

## 3. テストケース記述ルール

### 3.1 テストID体系
- テスト仕様ID: `TS-[主トレースID]`（例: `TS-FNC-006`）。
- テストケースID: `TC-[レベル]-[主トレースID]-[3桁]`。
- 例: `TC-IT-FR-012-001`, `TC-UAT-SCR-007-003`。

### 3.2 必須トレーサビリティ項目
各テストケースは以下を必須記載する。
- 要件: `FR` / `AC`（必要に応じ `NFR` / `CON`）。
- 設計: `FNC` / `SCR` / `IF` / `TBL` / `M`。
- 試験レベル: UT/IT/ST/UAT。

### 3.3 記述粒度ルール
- 前提条件: 実行可能な状態を具体的に記述（ユーザー、データ、時刻、画面）。
- 手順: 1手順1操作で記述し、分岐条件を明示する。
- 期待値: 画面/API/DB/ログの観測点を分離して記述する。
- 禁止事項: 「正しく表示される」「問題ない」等の非定量表現。

### 3.4 テスト設計技法の適用ルール
- 同値分割: 入力バリデーション（TZ、時刻、文字列長）。
- 境界値分析: `habit name 1/80/81`, `cutoff 00:00/23:59`。
- デシジョンテーブル: 同意要否、通知閾値判定。
- 状態遷移: `active -> archived -> active`、削除ジョブ `queued -> in_progress -> completed/failed`。
- ペアワイズ: TZ × cutoff × チェックイン時刻。

### 3.5 自動化フラグ
- 各ケースに `自動化対象`（Yes/No）と `理由` を記載する。
- 自動化優先: 認証同意、チェックイン冪等、退会SLA、RLS拒否、監査必須項目。

## 4. バグ報告ルール

### 4.1 重要度（Severity）
| 重要度 | 定義 | 例 |
| -- | -- | -- |
| Sev1 | サービス利用不可/法令重大違反 | ログイン不可、RLS破綻、削除漏れ |
| Sev2 | 主要業務に重大影響 | 同意フロー停止、チェックイン不整合 |
| Sev3 | 回避可能な機能不具合 | UI崩れ、軽微な導線不備 |
| Sev4 | 体裁/文言等の軽微不具合 | 文言誤字 |

### 4.2 優先度（Priority）
| 優先度 | SLA | 方針 |
| -- | -- | -- |
| P1 | 当日対応 | リリースブロック |
| P2 | 24h以内 | 原則リリース前修正 |
| P3 | 次スプリント | 影響を評価して計画修正 |
| P4 | 任意 | バックログ管理 |

### 4.3 バグ票必須項目
- タイトル、再現手順、期待結果、実際結果、発生環境、`trace_id`、添付証跡。
- 関連ID: `FR/AC/SCR/IF/TC-ID`。
- 発生頻度: Always / Intermittent / Once。

## 5. 合否判定基準

### 5.1 ケース単位
- Pass: 手順どおり実行され、期待値を全観測点で満たす。
- Fail: 期待値未達、または証跡不足で判定不能。
- Blocked: 前提未成立（環境障害等）。起因を明記して再実行。

### 5.2 フェーズ完了判定
- 実施率100%（Blockedは解消後再実行）。
- Sev1/P1 = 0件、Sev2/P2 = 0件（未解決）。
- Must ACの判定完了率100%。
- 受入証跡がレビュー可能な場所に保管済み。

## 6. 証跡管理ルール

### 6.1 証跡の最小セット
- 画面: スクリーンショット/動画。
- API: リクエスト/レスポンス（ヘッダ含む）。
- DB: 実行SQLと結果。
- ログ: `trace_id` と監査ログ行。

### 6.2 命名規則
- ファイル名: `[実施日]_[TC-ID]_[種別]`。
- 例: `20260316_TC-UAT-FR-023-001_db.csv`。
