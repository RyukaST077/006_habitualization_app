# 運用設計書 / 運用手順書

## 1. 運用方針 (SRE Principles)
### 1.1 運用ミッション
- 信頼性を機能の一部として扱い、`NFR-003/NFR-006/NFR-007/NFR-008`を継続達成する。
- 変更速度と安定性を両立するため、運用作業は自動化を優先し、手作業（Toil）を最小化する。
- 障害対応はBlamelessを原則とし、個人責任追及ではなく再発防止の仕組み改善に集中する。

### 1.2 適用スコープ
- 対象: Habimake MVP（Vercel Hobby, Supabase Free, GitHub Actions）
- 環境: Dev / Stg / Prod
- 法令対応: MVPはAPPI準拠を対象（海外法令は将来評価）

### 1.4 SLI / SLO / Error Budget（フェーズ2）
| SLI | 定義 | SLO（現時点） | 測定窓 | 備考 |
| -- | -- | -- | -- | -- |
| 可用性 | 成功リクエスト率（主要導線） | 99.5%/月 | 月次 | 内部SLO |
| レイテンシ | 主要画面P95応答時間 | 3.0秒以下 | 月次 | `NFR-001` |
| エラー率 | 5xx比率 | Warning `>=2%/10分` かつ `>=100 req`、Critical `>=5%/5分` かつ `>=50 req` | 日次/週次 | P1対象 |
| 認証健全性 | Auth失敗率 | Warning `>=15%/15分` かつ `>=40試行`、Critical `>=30%/5分` かつ `>=20試行` | 日次/週次 | P1対象 |
| 削除SLA | 退会不可化/完全削除達成率 | 60秒以内不可化、5分以内削除 | 日次 | `FR-023` |

| Error Budget対象 | 値 |
| -- | -- |
| 月間可用性SLO | 99.5% |
| 月間許容停止時間 | 約3時間36分 |

Error Budget運用ルール:
- 50%超消費: 変更リスクの高いリリースを制限し、安定化施策を優先。
- 80%超消費: 新機能リリースを原則停止し、信頼性改善を優先。
- 100%到達: 重大改善完了まで機能追加を凍結。

### 3.5 単独運用時の代替手順（人依存対策）
- 代替手順A: 運用責任者が30分以上応答不能の場合、`新規リリースを即時停止` し現行稼働を維持する（安全側制御）。
- 代替手順B: Sev-1時は「ロールバック」と「告知」だけを優先実施し、恒久対応は復帰後に分離する。
- 代替手順C: 手順実行順をRunbook化し、チェックリスト駆動で誤操作を防止する（REL/INC/DR IDで証跡化）。
- 代替手順D: 基盤障害は外部サポートへエスカレーションし、アプリ側は機能制限で影響最小化する。

## 4. 障害対応 (Incident Management)
### 4.1 障害レベル定義（フェーズ5）
| レベル | 定義 | 例 | 目標一次応答 | 目標復旧 |
| -- | -- | -- | -- | -- |
| Sev-1 | 全面停止/重大漏えい懸念 | ログイン不能、DB全面障害 | 15分以内 | 1時間以内に暫定復旧開始 |
| Sev-2 | 主要機能停止 | チェックイン不可、退会処理停止 | 15分以内 | 4時間以内 |
| Sev-3 | 一部機能劣化 | レイテンシ悪化、一部API失敗 | 60分以内 | 当日中 |
| Sev-4 | 軽微 | UI軽微不具合 | 翌営業日 | 計画対応 |

### 4.2 対応フロー
1. 検知（監視通知または問い合わせ）
2. 一次切り分け（認証/DB/アプリ/外部依存）
3. 暫定対応（ロールバック、設定戻し、機能制限）
4. 恒久対応（原因修正、テスト強化、監視改善）
5. 事後分析（Blameless Postmortem）
6. 再発防止追跡（アクション期限/担当を明確化）

### 4.3 ステータス通知方針
- 公開ステータスページがない場合、代替として公式Webお知らせを一次チャネルとして使用する。
- ログイン画面/メンテナンス画面を二次チャネルとして使用する。
- Sev-1/2は検知後30分以内に初報、以後60分ごとに更新。
- 解消後24時間以内に事後報告（影響範囲、原因、再発防止）を公開。

### 4.4 Blameless Postmortemテンプレート
- PM-001: 事象サマリ（いつ、何が、どれだけ）
- PM-002: タイムライン（検知〜復旧）
- PM-003: 影響範囲（利用者・データ・法令）
- PM-004: 直接原因/システム要因
- PM-005: うまく機能した点
- PM-006: 改善アクション（担当/期限/優先度）

### 4.5 エスカレーション
| 条件 | 一次 | 二次 | 三次 |
| -- | -- | -- | -- |
| Sev-1 | aliyell | Supabase/Vercelサポート | aliyell（法務/経営判断を兼務） |
| Sev-2 | aliyell | 関連開発者 | 必要時にaliyellが法務判断 |
| APPI該当 | Incident Commander | セキュリティ窓口 | 個人情報保護委員会報告フロー |

経営/法務エスカレーション基準（推奨確定値）:
- `Sev-1` または `個人情報漏えい疑い` を検知した時点で30分以内に経営判断者へ報告。
- APPI報告要否は初動60分以内に判定し、速報期限（3-5日）を起算する。

### 5.2 リストア手順（概要）
1. 復旧宣言（INC採番、復旧責任者任命）
2. 復旧ポイント確定（RPO内）
3. DB復元実施
4. アプリ接続確認、整合性確認
5. 監査ログ・セキュリティ観点の確認
6. サービス再開と監視強化

### 5.3 DR構成方針
- MVPはマネージド基盤依存で、アプリ側のマルチリージョン/アクティブアクティブは未採用。
- 主要戦略は「バックアップ復元 + 迅速な切り戻し」。
- 将来の有償化時にマルチリージョンDRを再評価する。

### 5.4 DR訓練計画
- 四半期に1回の机上訓練（削除失敗、認証障害、権限逸脱）
- 年1回の復元演習（RTO/RPO達成確認）
- 訓練結果はRunbookとRelease手順へ反映
